## B1. Microsoft Intune (Graph `deviceManagement/managedDevices`)
URLs: resource https://learn.microsoft.com/en-us/graph/api/resources/intune-devices-manageddevice?view=graph-rest-1.0 ; list https://learn.microsoft.com/en-us/graph/api/intune-devices-manageddevice-list?view=graph-rest-1.0 ; wipe https://learn.microsoft.com/en-us/graph/api/intune-devices-manageddevice-wipe?view=graph-rest-1.0 ; permissions https://learn.microsoft.com/en-us/graph/permissions-reference ; detectedApp https://learn.microsoft.com/en-us/graph/api/resources/intune-devices-detectedapp?view=graph-rest-1.0 ; throttling https://learn.microsoft.com/en-us/graph/throttling-limits ; app-only flow https://learn.microsoft.com/en-us/graph/auth-v2-service
- Auth: OAuth 2.0 client credentials with app registration (secret, certificate or federated credential), `scope=https://graph.microsoft.com/.default`, token endpoint `login.microsoftonline.com/{tenant}/oauth2/v2.0/token`; application permissions always need admin consent (consent via Entra admin center or `/adminconsent` URL). Intune Graph requires an active Intune license for the tenant. [auth-v2-service], [resource page]
- Read-only scope: `DeviceManagementManagedDevices.Read.All` (application + delegated) - "read the properties of devices managed by Intune". [permissions-reference]; list endpoint accepts Read.All or ReadWrite.All [list page]. `ReadWrite.All` "does not allow high impact operations such as remote wipe and password reset". [permissions-reference]
- Inventory fields (managedDevice v1.0): id, deviceName, managedDeviceName, operatingSystem, osVersion, model, manufacturer, serialNumber, imei, meid, phoneNumber, wiFiMacAddress, ethernetMacAddress (select only), enrolledDateTime, lastSyncDateTime (filterable lt/gt), deviceEnrollmentType, enrollmentProfileName, complianceState (compliant/noncompliant/conflict/error/inGracePeriod/...), complianceGracePeriodExpirationDateTime, isEncrypted, isSupervised, jailBroken, managedDeviceOwnerType (company/personal), userId, userPrincipalName, userDisplayName, emailAddress, azureADDeviceId, azureADRegistered, managementAgent, deviceHealthAttestationState (BitLocker, secure boot, TPM...), totalStorageSpaceInBytes, freeStorageSpaceInBytes, physicalMemoryInBytes, androidSecurityPatchLevel, partnerReportedThreatState, notes. Some fields (activationLockBypassCode, iccid, udid, notes, MACs, memory) are only returned with `$select` on a single GET. [resource page]
- Installed apps: `detectedApp` resource (displayName, version, publisher, platform, sizeInByte, deviceCount; unmanaged apps only for corporate-owned devices) listed at `/deviceManagement/detectedApps` with relationship `managedDevices`. The per-device path `managedDevices/{id}/detectedApps` is not shown on the pages read: not confirmed. [detectedApp page]
- Actions (methods on managedDevice) [resource page]: retire, wipe, resetPasscode, remoteLock, requestRemoteAssistance, disableLostMode, locateDevice, bypassActivationLock, rebootNow, shutDown, recoverPasscode, cleanWindowsDevice, logoutSharedAppleDeviceActiveUser, deleteUserFromSharedAppleDevice, syncDevice, windowsDefenderScan, windowsDefenderUpdateSignatures, updateWindowsDeviceAccount.
  - wipe: application and delegated permission `DeviceManagementManagedDevices.PrivilegedOperations.All` (only); body keepEnrollmentData, keepUserData, macOsUnlockCode, obliterationBehavior, persistEsimDataPlan; 204 on success. [wipe page]
  - PrivilegedOperations description: "perform remote high impact actions such as wiping the device or resetting the passcode". [permissions-reference]
  - Per-action permission for retire, remoteLock, syncDevice, rebootNow etc.: not individually confirmed (only wipe page read). Verify each action page before shipping. App deployment/assignment (mobileApps) and policy assignment: permission names (DeviceManagementApps.ReadWrite.All, DeviceManagementConfiguration.ReadWrite.All) appear in Microsoft's reference but the specific pages were not read: not confirmed.
- Webhooks/notifications: Intune `managedDevice` is NOT in the Graph change-notification supported resource table (only users, groups, etc.), so polling is required. [https://learn.microsoft.com/en-us/graph/change-notifications-overview] Delta query exists for Entra `device` (see B2); for managedDevices: not confirmed.
- Rate limits: Intune devices (managedDevice etc.): per tenant 4,000 requests / 20 s total, 2,000 per app per tenant; writes 400 / 20 s per tenant, 200 per app. Other Intune resources: 2,000/1,000 per 20 s; writes 200/100. [throttling-limits]. Global: 130,000 requests / 10 s per app across tenants.
- Multi-tenant/MSP: one multi-tenant app registration + per-customer admin consent (`/adminconsent` URL, tenant ID per customer) with token requested per customer tenant. Under GDAP, Microsoft's partner guide says multitenant application-only consent is not supported through GDAP and must be done manually by a customer admin (consent URL); delegated (app+user) calls work with active GDAP relationships. [https://learn.microsoft.com/en-us/partner-center/developer/gdap-and-secure-application-model], [https://learn.microsoft.com/en-us/partner-center/customers/gdap-faq] (read via search summaries; wording not verified on the page itself: partly not confirmed). Plan: treat each customer as its own tenant record (tenant ID + consent state), never a single global token.

## B2. Microsoft Entra ID devices
URLs: https://learn.microsoft.com/en-us/graph/api/resources/device?view=graph-rest-1.0 ; permissions https://learn.microsoft.com/en-us/graph/permissions-reference ; throttling https://learn.microsoft.com/en-us/graph/throttling-limits
- Auth: same client-credentials app model. Read: `Device.Read.All` ("read your organization's devices' configuration information"). Write: `Device.ReadWrite.All` ("does not allow device creation, deletion or update of alternative security identifiers"). [permissions-reference]
- Inventory fields: id, deviceId, displayName, operatingSystem, operatingSystemVersion, manufacturer, model, trustType (Workplace/AzureAd/ServerAd), isCompliant, isManaged, managementType, mdmAppId, isRooted, deviceOwnership, enrollmentType, enrollmentProfileName, registrationDateTime, approximateLastSignInDateTime, complianceExpirationDateTime, accountEnabled, onPremisesSyncEnabled, extensionAttributes 1-15, profileType; relationships registeredOwners, registeredUsers, memberOf. No encryption state or installed apps (use Intune for those). [device resource]
- Actions: accountEnabled can be set only by callers with at least Cloud Device Administrator (disable device); delete device; add/remove registered owners/users. No lock/wipe (those are Intune). [device resource]
- Change tracking: `device: delta` supported. Change notifications for devices are not in the supported-resource table (only user/group) [change-notifications-overview].
- Rate limits: device writes 3,000 / 2.5 min per app per tenant; 25 / 10 s per user per tenant; resource-unit quota per app+tenant 3,500 (S) / 5,000 (M) / 8,000 (L) per 10 s. [throttling-limits]
- Multi-tenant: as B1; Entra devices and Intune managedDevices can be joined via `azureADDeviceId` = Entra `deviceId`. (inference from the field descriptions)

## B3. Jamf Pro
URLs: overview https://developer.jamf.com/jamf-pro/docs/jamf-pro-api-overview ; client credentials https://developer.jamf.com/jamf-pro/docs/client-credentials ; which API https://developer.jamf.com/jamf-pro/docs/which-api-should-i-use ; privileges https://developer.jamf.com/jamf-pro/docs/privileges-and-deprecations ; scalability https://developer.jamf.com/jamf-pro/docs/jamf-pro-api-scalability-best-practices ; webhooks https://developer.jamf.com/jamf-pro/docs/webhooks-1 ; reference index https://developer.jamf.com/jamf-pro/reference/llms.txt
- Two APIs: Jamf Pro API at `/api` (docs at `/api/doc` on the instance; JSON; filtering/sorting/pagination; endpoint versioning; new features land here first) and Classic API at `/JSSResource` (XML, JSON on GET). Jamf says Classic "is not going anywhere, anytime soon" but recommends Pro API. [which-api]
- Auth: (a) API Roles + API Clients: OAuth client credentials (Jamf Pro 10.49.0+, works for Classic and Pro APIs), client secret exchanged for a short-lived access token (lifetime not stated on the page read: not confirmed). (b) Username/password -> `POST /v1/auth/token` Bearer token, expires after 20 minutes, `/v1/auth/keep-alive` renews; SSO not supported for API. [jamf-pro-api-overview], [client-credentials]
- Granularity: API Role = set of privileges (per endpoint family, e.g. "Read Computers", "Read Mobile Devices", "Send Computer Remote Wipe Command", "Send Mobile Device Remote Wipe Command", "View MDM command information in Jamf Pro API"); client gets cumulative roles; adding/removing a role from a client requires rotating the secret; privilege changes apply to new tokens immediately. CRUD privileges map to POST/GET/PUT/DELETE. A read-only role is therefore feasible. [client-credentials], [privileges page], [reference pages]
- Inventory: `GET /v4/computers-inventory` (section=GENERAL, HARDWARE, ...; older v1-v3 deprecated, v3 deprecated 2026-07-14) with "Read Computers"; mobile `GET /v2/mobile-devices` and `/v2/mobile-devices/detail` with "Read Mobile Devices". Detailed per-field list (OS, version, encryption/FileVault, apps, last check-in, ownership, user) not enumerated here: not confirmed field by field; sections exist in the ComputerSectionV4 enum on the reference page. [reference pages]; Classic computer inventory endpoints have a documented deprecation guide: https://developer.jamf.com/jamf-pro/docs/deprecation-of-classic-api-computer-inventory-endpoints
- Actions: `POST /v4/computers-inventory/{id}/erase` ("Send Computer Remote Wipe Command"); `POST /v2/mobile-devices/{id}/erase` ("Send Mobile Device Remote Wipe Command"); `POST /v2/mdm/commands` queues an MDM command (commandType discriminator includes DEVICE_LOCK, ENABLE_LOST_MODE, CLEAR_PASSCODE, DEVICE_LOCATION, DEVICE_INFORMATION, DELETE_USER, DECLARATIVE_MANAGEMENT, CERTIFICATE_LIST, ...; full list not captured); "a separate privilege is required for each device type and MDM command"; `post_v2-mdm-blank-push`; `v1/computer-inventory/{id}/remove-mdm-profile` ("Send Computer Unmanage Command"). Policy/app assignment: not confirmed. [reference pages, mdm-commands page https://developer.jamf.com/jamf-pro/reference/post_v2-mdm-commands]
- Webhooks: outbound HTTP POST on events: ComputerAdded, ComputerCheckIn, ComputerInventoryCompleted, ComputerPolicyFinished, ComputerPatchPolicyCompleted, ComputerPushCapabilityChanged, DeviceAddedToDEP, MobileDeviceCheckIn, MobileDeviceCommandCompleted, MobileDeviceEnrolled, MobileDeviceInventoryCompleted, MobileDeviceUnenrolled, MobileDevicePushSent, PushSent, PatchSoftwareTitleUpdated, RestAPIOperation, SCEPChallenge, SmartGroupComputer/MobileDevice/UserMembershipChange, JSSStartup, JSSShutdown; JSON or XML bodies with `webhook.eventTimestamp/id/name/webhookEvent`. [webhooks-1] Webhook authentication options (None / Basic / Header key-values) are documented in older admin guide versions (https://docs.jamf.com/10.34.0/jamf-pro/documentation/Webhooks.html, via search); no HMAC signing, retry or delivery-guarantee statement found: not confirmed. Webhooks CRUD in Classic API (`/webhooks`).
- Rate limits: "Jamf Pro does not have a built-in solution to restrict or limit the number of API requests"; guidance: at most 5 concurrent connections, measure response times, exponential backoff. [scalability page]
- Multi-tenant: Jamf Pro is one server instance per customer (or a single instance with sites; sites not researched). Plan one connection record (base URL + client id/secret) per customer instance. (inference; sites/multi-tenancy not confirmed on official page read)

## B6. Apple Business Manager API (now "Apple Business" API)
URLs: landing https://developer.apple.com/documentation/apple-school-and-business-manager-api ; OAuth https://developer.apple.com/documentation/apple-school-and-business-manager-api/implementing-oauth-for-the-apple-school-manager-and-apple-business-api ; endpoints https://developer.apple.com/documentation/applebusinessapi ; webhooks https://developer.apple.com/documentation/apple-school-and-business-manager-api/understanding-apple-business-api-webhook-events ; changelog https://developer.apple.com/documentation/apple-school-and-business-manager-api/apple-school-manager-and-apple-business-api-changelog ; account setup https://support.apple.com/guide/business/create-an-api-account-axm33189f66a/web
- Positioning: automation of device management assignment and read access to devices that enroll via Automated Device Enrollment (ADE) plus (Apple Business) users, groups, blueprints, configurations, packages, apps, audit events. It is NOT an MDM command channel (no lock/wipe/lost mode). Apple's network guide says that in April 2026 Apple Business Manager/Essentials were replaced by "Apple Business" (https://support.apple.com/en-us/101555 via search; verify). API host `https://api-business.apple.com/v1` (examples in docs).
- Auth: OAuth 2 client-credentials with a signed JWT client assertion. API account created by an Organization Administrator in the portal (Settings > API); private key (.pem) generated once; up to 50 API accounts. Assertion: header alg `ES256`, `kid` = keyId; claims `iss`/`sub` = clientId (docs list `sub`), `aud` = `https://account.apple.com/auth/oauth2/v2/token`, `iat`, `exp` (< 180 days after iat), `jti`. Token request `POST https://account.apple.com/auth/oauth2/token` with `grant_type=client_credentials`, `client_id`, `client_assertion_type=urn:ietf:params:oauth:client-assertion-type:jwt-bearer`, `client_assertion`, `scope=business.api` (school: `school.api`). Access token TTL 3600 s. [OAuth page], [support page]
- Permissions (set on the API account, granular, named in UI): view device management services and add devices with Apple Configurator; assign devices to a device management service; unassign/release devices; schedule/update/cancel MDM migration; get Activation Lock status; view users / user groups / OUs; view/manage blueprints; view/create-edit-delete configurations; packages; view apps; access audit events. Read-only is feasible. [support page]
- Inventory: `GET /v1/orgDevices` (ADE devices, filters: serial number, product family Mac/iPhone/iPad/iPod/AppleTV/Watch/Vision, purchase source APPLE/RESELLER/MANUALLY_ADDED, order number, assignment ASSIGNED/UNASSIGNED, date added/ordered), device info, assigned MDM server id/info, Activation Lock status, AppleCare coverage per device, MDM-enrolled devices of Apple's built-in device management; `GET /v1/mdmServers` and devices per server. Not available: OS version, last check-in, compliance, encryption, installed apps for third-party-MDM devices (those live in the MDM). Exact attribute list of orgDevice not read: not confirmed. [endpoint index JSON]
- Actions: `POST /v1/orgDeviceActivities` with activityType ASSIGN_DEVICES / UNASSIGN_DEVICES / release / ASSIGN_DEVICES_WITH_MDM_MIGRATION_DEADLINE (MDM migration without erase); create/update/delete MDM servers (device management services), blueprints/configurations/packages. Requires matching permissions above. [endpoint index], [orgdeviceactivity page]
- Webhooks (new): create/update/delete webhooks via `/v1/webhooks`; event types ORG_DEVICE_ATTRIBUTE_CHANGED, ORG_DEVICE_ATTRIBUTE_MIGRATION_DETAILS_CHANGED, ORG_DEVICE_RELATIONSHIP_ASSIGNED_SERVER_CHANGED, ORG_DEVICE_RELATIONSHIP_WARRANTY_CHANGED; HTTPS POST JSON; HMAC SHA-256 authenticity via `x-apple-signature: hmacsha256=<hex>` using the secret set at creation; deliveries listable and retryable via API (`/webhooks/{id}/deliveries`, retry delivery), ping endpoint exists. [webhook page], [changelog]
- Rate limits: responses document "429 Too Many Requests" but no numeric limit found: not confirmed.
- Multi-tenant: one organization = one API account/key; MSP needs a credential per customer ABM org (each customer admin creates it); no partner delegation documented: not confirmed (inference). Admin audit events exist, useful for compliance.

## B7. Android Enterprise (Android Management API, AMAPI)
URLs: overview https://developers.google.com/android/management ; devices https://developers.google.com/android/management/reference/rest/v1/enterprises.devices ; issueCommand https://developers.google.com/android/management/reference/rest/v1/enterprises.devices/issueCommand ; delete https://developers.google.com/android/management/reference/rest/v1/enterprises.devices/delete ; notifications https://developers.google.com/android/management/notifications ; service account https://developers.google.com/android/management/service-account ; quotas https://developers.google.com/android/management/permissible-usage
- Auth: Google Cloud service account (key file) with IAM role Android Management User (`roles/androidmanagement.user`, permission `androidmanagement.enterprises.manage`) in a project with the API enabled; OAuth scope `https://www.googleapis.com/auth/androidmanagement` (single scope: no read-only scope documented, and the role is manage-level). [service-account], [issueCommand]
  - Granularity: read-only is not available via scope/role as documented (not confirmed that a viewer role exists). Enforce read-only in our own code. (inference)
- Inventory: `enterprises.devices.list/get`; fields state/appliedState, ownership, managementMode, hardwareInfo (brand, model, manufacturer, serial), softwareInfo (Android version, build, security patch; needs policy `softwareInfoEnabled`), applicationReports (needs `applicationReportsEnabled`), lastStatusReportTime, lastPolicySyncTime, policyCompliant, nonComplianceDetails, enrollmentTime, user, securityPosture (SECURE/AT_RISK/POTENTIALLY_COMPROMISED), policyName. Encryption state: not confirmed on the page read (may sit in a policy-reported field). [devices page]
- Actions: `issueCommand` types LOCK, RESET_PASSWORD, REBOOT, RELINQUISH_OWNERSHIP, CLEAR_APP_DATA, START_LOST_MODE, STOP_LOST_MODE, ADD_ESIM, REMOVE_ESIM, REQUEST_DEVICE_INFO, WIPE (factory reset on company-owned; work-profile delete on personal; runs after device acknowledges; cancellable until then). `devices.delete` (HTTP DELETE) also wipes with `wipeDataFlags` and `wipeReasonMessage` (<=200 chars) and removes the device record. `devices.patch` changes state (ACTIVE/DISABLED), assigned policy. App deploy / policy assignment: via policies resource + patch (policies reference not read: not confirmed). All need the same scope. [issueCommand], [delete], [devices page]
- Notifications: Cloud Pub/Sub push or pull; notification types ENROLLMENT, STATUS_REPORT (Device), COMMAND (Operation), USAGE_LOGS, ENTERPRISE_UPGRADE; set `pubsubTopic` and `enabledNotificationTypes` on the enterprise; grant `android-cloud-policy@system.gserviceaccount.com` the Pub/Sub Publisher role; data is base64 JSON; test message on setup. Authentication of receipt is via Pub/Sub IAM (no custom signature). Latency best-effort; some app events up to 60 min. [notifications page]
- Rate limits: default 1,000 queries per 100 s per project; 60 queries per minute per (action, EMM id, enterprise id, policy/device id); initial quota up to 500 devices, increase via request form; max 2 projects per developer. [permissible-usage page via search; ~8 months old, re-check]
- Multi-tenant: the service-account page says do not create a separate Cloud project per customer; instead one project with one Android enterprise per customer (`enterprises/{id}`), bound by the customer through the signup flow (signup-URL flow not on pages read: not confirmed). Via an EMM (e.g. Intune `managementAgent` values or Jamf-like partners) the device data comes through that EMM's API instead. [service-account page]; EMM vs direct usage: not confirmed.

# PLANNING TAKEAWAYS (inference, not vendor statements)
---------------------------------------------------------------------
1. Comet: poll `get-jobs-for-date-range` + `list-users-full` with a read-only (PreventWriteActions) admin or token; optionally add webhook for job completion with a static header secret and 5-minute reconcile poll. Actions via a separate write-capable admin; require live connection and show "device offline" gracefully.
2. Credential store per customer: Intune/Entra (tenant id + app id + secret/cert, consent state), Jamf (URL + API client), Iru/Kandji (subdomain + region + token), ABM (client id + key id + .pem), AMAPI (service account + enterprise id), Mosyle (blocked until docs obtained).
3. Read-only scopes exist for Intune/Entra, Jamf, Iru, ABM (permission checkboxes). Android has only a single manage scope.
4. Event push: Apple (HMAC signed), Jamf, Comet (header-secret), Android (Pub/Sub). Intune, Entra, Iru: poll.
5. Destructive actions (wipe/erase/retire) should be a separate, explicitly enabled capability with approval; Intune requires the separate PrivilegedOperations permission, which makes opt-in clean.
