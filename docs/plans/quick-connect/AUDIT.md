# Secure HTTPS Quick Connect: audit of the existing Agit8or Connect implementation

Status: **audit**. Nothing in this document was implemented by the commit that added it. Findings fixed later are
marked "Fixed in increment A" (roadmap 79.8) in the findings table. Base: `origin/main`
at `d34634ff` (v3.17.739). All paths are relative to the repository root. `file:line` references are to that commit.

Legend: **Implemented** = meets the requirement as written · **Partial** = some of it exists · **Missing** = nothing
exists · **Conflicts** = something exists that works against the requirement and has to change or be bypassed.

Test run used for behaviour checks (targeted, in the audit worktree): `manage.py test connect api_access` and
`python -m unittest discover -s agit8or_connect/tests -t .` (results at the end of this file).

## 4. Security findings in the current code

No **Critical** finding: every protocol operation is authenticated by Ed25519 signatures or DPoP-bound tokens, and
those checks are correct as far as this audit could verify (sections 2.6–2.7). The findings below are gaps
in network control, availability, and robustness. None are fixed here.

| Id | Severity | Finding | Evidence | Failure scenario |
|---|---|---|---|---|
| QC-01 | **High** | Connect endpoints are reachable from any source by default; their only network control is the general REST API policy (shared mode, no Connect-specific or per-connection layer). | `api_access/groups.py:15,48-49`; `api_access/models.py:56`; `api_access/policy.py:260-261` | An admin enables Connect on an Internet-facing install. Pairing, token, events, JWKS, health and discovery are open to the whole Internet, which makes QC-02 and QC-03 exploitable by anyone. If the admin restricts the REST API to the office range, Connect peers are also cut off, so admins will avoid using the allowlist. |
| QC-02 | Medium | Unauthenticated denial of pairing: each wrong-code pairing request counts against **every** open invitation; five burn them all. The global pairing bucket (60 per 10 min per worker) can also be exhausted. | `connect/pairing.py:339-352, 372-378`; `connect/ratelimit.py:11`; installation id is public at `views_api.py:83-97` | An attacker reads the installation id from `/.well-known/agit8or-connect`, signs five requests with a throw-away key and wrong codes, and repeats every few minutes. No administrator can complete a pairing. |
| QC-03 | Medium | **Fixed in increment A (partial):** `token.issue` refusals without a known connection and wrong pairing codes now go to the folded `ApiAccessDecision` log and one `refusals.summary` chain record per minute (`connect/denials.py`). Refused sources (QC-01) remain for B1. Unauthenticated callers can write permanent rows into the append-only audit chain, and each write takes a row lock on `InstallationIdentity`. | `connect/auth.py:110-116` (denied token requests, unknown `client_id`); `connect/pairing.py:374-375`; `connect/audit_log.py:49-60` | At 1,200 token requests per minute per worker (4 workers), about 4,800 rows a minute are added that can never be pruned. Serialised `SELECT … FOR UPDATE` writes on SQLite (prod) stall other writes; long SQLite writes are known to cause login 400s on this host. Legitimate audit records queue behind attacker rows. |
| QC-04 | Medium | **Fixed in increment A:** Connect builds its own `OutboundPolicy` (`allow_local=False`, port 443 + the explicit `base_url` port) and never calls `configured_service_policy()` (`connect/transport.py`, `agit8or_connect/adapters/safe_http.py`). Connect's outbound policy inherits the global `ALLOW_PRIVATE_IP_INTEGRATIONS` opt-in. When it is on, loopback, the rest of 169.254/16 and all private ranges are reachable on **any port**, even for connections with "private network" off. This contradicts PROTOCOL.md §4. | `agit8or_connect/adapters/safe_http.py:42-47`; `core/safe_http.py:145-148, 187-206` | The opt-in is common on installs with LAN PSA/RMM. A pairing-code holder sends `discovery_url=https://intra.example.com:8443/` (a name resolving to 10.x or 127.0.0.1). Opening the request review page triggers the fetch. Only TLS validation limits it: services with a valid certificate for that name are reached, and error messages ("could not be reached" vs "TLS verification failed") reveal open ports. The opt-in is **not** set on this host. **Reproduced** in the audit worktree: with `ALLOW_PRIVATE_IP_INTEGRATIONS=True`, `SafeHttpTransport(allow_private=False)._policy()` is `OutboundPolicy(allow_lan=True, allow_local=True, allowed_ports=None)` and `is_allowed_ip` is True for `127.0.0.1` and `169.254.1.1`. |
| QC-05 | Medium | No pinned outbound destination. Each request re-resolves DNS. No approved IP set, port, or certificate/SPKI pin is stored, and a changed address is accepted silently as long as some CA-valid certificate is presented. Event bodies are signed, not encrypted, so their confidentiality rests on TLS alone. | `connect/transport.py:25-27`; `connect/models.py:76-93`; `connect/events.py:62-69` | A DNS hijack plus a mis-issued or ACME-obtained certificate for the peer hostname silently redirects deliveries. The attacker receives every queued `alert.*` event (customer data) without a warning, because nothing compares the new address with the approved one. Token requests would fail without the peer key, but events are pushed before that matters. |
| QC-06 | Medium | Events dead-letter after 12 attempts (about 7–8 h) and are never retried automatically. Revocation cancels everything still queued. | `agit8or_connect/webhooks.py:139-145`; `connect/events.py:82-85`; `connect/lifecycle.py:68` | A peer is down over a weekend. Monday morning every alert event of the outage sits in the dead-letter list and was never delivered. |
| QC-07 | Medium | The connection shows "Connected" (`ACTIVE`) as soon as both sides approve, before any token, permission or connectivity check. | `connect/pairing.py:318-322`; `connect/models.py:59` | The peer's JWKS route is blocked by its proxy, or its endpoints point at the wrong host. The UI says Connected and the scheduler starts delivering, but every token request fails. Staff discover it only when alerts are missing. |
| QC-08 | Low | **Fixed in increment A:** `approve_inbound`, `approve_local`, `finalize_*`, `_activate` and the `app_connection` applier refuse while the kill switch is engaged. Approval paths ignore the kill switch. `approve_inbound`, `approve_local`, `finalize_*` and the `app_connection` applier can make a connection `ACTIVE` while the switch is engaged. It then stays active after release, contrary to PROTOCOL.md §12 ("Releasing it does not resume them"). | `connect/pairing.py:279-306, 437-491`; `connect/approvals.py:15-34`; compare `lifecycle.resume` (`connect/lifecycle.py:50-51`) | During an incident the admin engages the kill switch. A second admin approves a pending protected change. When the switch is released, that connection is live without anyone resuming it. |
| QC-09 | Low | **Fixed in increment A:** the CA bundle is loaded from memory and the client certificate/key through an anonymous `memfd`; fallback 0600 file in a private 0700 directory, removed in `finally`, plus a start-up sweep. The mTLS client private key (and CA bundle) is written in plaintext to a temp file in the system temp directory on every request. It is removed in `finally`, so it survives a worker kill or OOM. | `agit8or_connect/adapters/safe_http.py:77-84, 104-117` | A worker is killed mid-request, the decrypted client key stays in `/tmp/a8c-*.pem` (0600, owned by the app user) until cleanup. Backups or debug bundles of `/tmp` capture it. |
| QC-10 | Low | **Fixed in increment A:** `AGIT8OR_CONNECT_PUBLIC_URL` is required for invitations, outbound pairing and approval; `public_base()` raises instead of returning a relative URL. `AGIT8OR_CONNECT_PUBLIC_URL` is optional. Without it, request-less calls produce relative URLs: the initiator's pairing request carries `discovery_url="/.well-known/agit8or-connect"`, and the approval result's `endpoints` are path-only. With a request, `htu`/`aud` follow the `Host` header. | `connect/identity.py:50-58`; `connect/pairing.py:140, 486` | An admin enables Connect without the setting. Pairing appears to work, but the responder cannot look the initiator up (approval fails with a discovery error), and the result tells the peer path-only endpoints. Behind several `ALLOWED_HOSTS`, the token audience depends on which name the peer used. |
| QC-11 | Low | **Fixed in increment A:** GET of the review page makes no outbound request; "Look up the other application" is a POST. A state-changing GET: opening a request review page fetches the code holder's chosen `discovery_url` and saves the result. | `connect/views_ui.py:202-208` | An admin follows a link (or a prefetcher loads it) and Clientst0r contacts an address the unauthenticated code holder chose. Bounded by the SSRF guard, but it is an outbound request with no deliberate admin action. |
| QC-12 | Low | **Fixed in increment A:** the review page warns, and approval opens a `tech_access` protected change (`app_connection`) needing a second administrator. An inbound request may claim the installation id of an existing connected peer, and no warning is shown. The outbound duplicate check exists only on the initiator side. | `connect/pairing.py:379-395` vs :123-127 | A leaked code lets an attacker submit a request posing as the installation id of the MSP's real Rem0te. The review page shows a familiar id; only the address and SAS differ. |
| QC-13 | Low | Rate limits live in the per-process cache: four workers give four times the documented limits, and counters reset on reload. The code brute-force limit is durable (database). | `connect/ratelimit.py:1-29`; `config/settings.py:283-292` | Pairing/token/event floods get four times the intended budget. This makes QC-02 and QC-03 cheaper. |
| QC-14 | Low | **Fixed in increment A:** `get_token`/`call` re-read the state from the database and raise `connection_inactive` unless active. `client.get_token` / `client.call` do not check the connection state, and the in-process token cache is not cleared in other workers on suspend or revoke. All current callers check the state themselves. | `connect/client.py:20-70`; `connect/lifecycle.py:41, 70` | Code added later (for example Phase 79.7 device sync) calls `client.call` on a suspended connection. Another worker's cached token (≤300 s) lets the call through on the peer side. |
| QC-15 | Low | Unauthenticated triggers of outbound requests: a token request or event naming an unknown `kid` makes Clientst0r fetch the peer's JWKS (at most once a minute per connection). | `connect/auth.py:43-65, 95-99`; `connect/events.py:126-129` | Anyone who knows a connection UUID causes one outbound request per minute to the peer. With QC-01, this is visible to the whole Internet. |
